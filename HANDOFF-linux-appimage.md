# Handoff: Toolport's Linux AppImage fails on Arch / Omarchy

Written 2026-08-19 from an Omarchy (Arch + Hyprland + Wayland) VMware guest where
`Toolport_1.14.0_amd64.AppImage` could not be made to work. Everything below was
reproduced and verified on that machine, not inferred.

**Goal for this session:** fix these upstream so the app works on modern
Wayland/rolling distros *without changing behaviour for existing Debian/Ubuntu
users*. Both fixes below are additive.

---

## Symptom as the user sees it

1. First launch: `Could not create default EGL display: EGL_BAD_PARAMETER. Aborting...`,
   no window, and **Xwayland dies session-wide** — which then breaks other apps
   (browser launching, `xdg-open`) until the user logs out.
2. Every launch after that: nothing at all. No output, no window, no error. It
   just sits there.
3. If you get past those: the window opens **grey and empty**.

They are three faces of two independent bugs.

---

## Bug 1 — the AppImage forces X11, unconditionally

`AppRun` sources `apprun-hooks/linuxdeploy-plugin-gtk.sh`, generated by
`linuxdeploy-plugin-gtk`. Line 9:

```sh
export GDK_BACKEND=x11 # Crash with Wayland backend on Wayland - We tested it without it and ended up with this: https://github.com/tauri-apps/tauri/issues/8541
```

Because the hook is sourced *after* the caller's environment, **nothing the user
sets can override it**. Setting `GDK_BACKEND=wayland` yields only
`Gdk-Message: Trying x11 backend` and then a tao panic,
`Failed to initialize gtk backend!`.

Why that is fatal here rather than merely suboptimal: on this guest's `vmwgfx`
driver, Xwayland dies the moment the app renders through it —

```
XWAYLAND: wl_display#1: error 1: invalid arguments for wl_surface#18.attach
```

— and Hyprland does not respawn it. `DISPLAY=:0` still points at a socket the
compositor holds, so every later launch *connects and then blocks forever* in
`unix_wait_for_peer`. That is symptom 2, and it is why there is no error message:
the process is alive and waiting, not failing.

`WEBKIT_DISABLE_DMABUF_RENDERER=1` does **not** prevent the Xwayland death. It was
tested on a clean boot; Xwayland still died.

### Suggested fix

Make the forced backend a default rather than an override — a one-line change
that leaves Ubuntu/Debian behaviour byte-identical:

```sh
export GDK_BACKEND="${GDK_BACKEND:-x11}"
```

The hook is generated by linuxdeploy, so this needs a post-bundle step in
`.github/workflows/release.yml` (after `tauri build --bundles appimage`):
unpack the produced AppImage with `--appimage-extract`, `sed` that one line,
repack with `appimagetool`, then re-sign. Fail the build if the expected line is
not found, so a linuxdeploy change cannot silently drop the patch.

Worth checking first whether tauri-apps/tauri#8541 is still real with the current
wry/tao. If it is fixed, drop the forcing entirely instead.

---

## Bug 2 — the bundled WebKit cannot do EGL against current Mesa

With Bug 1 patched out locally, the app started on Wayland but the window was
grey: the GTK shell ran while `WebKitWebProcess` aborted on every launch with
`EGL_BAD_PARAMETER` (SIGABRT, `si_code: SI_TKILL` — it calls `abort()` on itself).

The bundle ships Ubuntu 22.04's `libwebkit2gtk-4.1`, which release.yml links
against (`scripts/ci-apt-install.sh libwebkit2gtk-4.1-dev`, runner
`ubuntu-22.04`). It is old enough to have no `WebKitGPUProcess` at all. It cannot
initialise EGL against Arch's Mesa 26.x.

**This is the bundle, not the machine.** Both checks were run on the failing host:

- `eglinfo -B -p wayland|gbm|surfaceless` — all healthy (llvmpipe GL 4.6 on
  wayland, SVGA3D 4.3 on gbm).
- A ~10-line python-gobject `WebKit2 4.1` WebView using the *system* WebKitGTK
  2.52.5 renders fine on the same session.

None of `WEBKIT_DISABLE_DMABUF_RENDERER`, `WEBKIT_DISABLE_COMPOSITING_MODE`, or
`WEBKIT_FORCE_SANDBOX=0` avoids it, alone or combined.

### What actually fixed it locally

Unpack the AppImage and move every bundled `usr/lib/*.so*` whose filename also
exists in `/usr/lib` out of the way (121 libraries), plus the bundled
`webkit2gtk-4.1` helper dir and `gstreamer-1.0` plugins, so the app links against
system WebKit/GStreamer/glib. Anything the host lacks stays bundled.

Note it **cascades** — displacing only WebKit is not enough. Each round surfaces
the next ABI mismatch as an `undefined symbol`: system GStreamer wants
`gst_debug_log_id`, then system glib wants `g_once_init_leave_pointer`. Only
displacing all shadowing libraries at once converges.

That local workaround lives at `~/.local/bin/toolport` on the reporting machine.
It is a workaround, not a shippable fix.

### Suggested fix — ship a native package for Arch

The honest conclusion is that an AppImage bundling WebKit cannot be made robust
across rolling distros: the bundled browser engine and the host GPU stack must
agree, and on a rolling release they will not. Rather than fight it:

1. **AUR package** (`toolport-bin`) that repackages the existing `.deb` payload
   and declares real dependencies: `webkit2gtk-4.1`, `gtk3`, `libsoup3`,
   `libayatana-appindicator`, `gstreamer`. This is the idiomatic Arch answer and
   sidesteps the bundle completely. Omarchy users would then
   `omarchy pkg aur add toolport-bin`. Lowest effort, highest payoff — the `.deb`
   is already built in CI.
2. Optionally a **Flatpak**, which solves the same problem generally by pinning a
   real runtime.
3. Optionally a second "slim" AppImage that excludes webkit/gstreamer from
   bundling and requires host WebKitGTK — but do not make it the default download.

Keep the fat AppImage as-is for Ubuntu/Debian. It works there.

## Verification matrix

- Ubuntu 22.04 / 24.04 — fat AppImage, X11 and Wayland sessions. Must be
  unchanged.
- Arch (ideally Omarchy, Hyprland, Wayland) — native package renders content;
  `pgrep -x Xwayland` still returns a PID after launch and quit.
- Any Wayland session — `GDK_BACKEND=wayland ./Toolport.AppImage` should now be
  honoured rather than silently ignored.

## Reproducing the "silent hang" for testing

It only appears once Xwayland is dead, so: launch the unpatched AppImage on a
Wayland session whose Xwayland is fragile, confirm `pgrep -x Xwayland` is empty,
then launch again. Diagnose with `cat /proc/<pid>/task/*/wchan` — `unix_wait_for_peer`
means it is blocked connecting to the orphaned X socket.

Note the AppImage wrapper process is **not** the app; the real binary is
`usr/bin/conduit`. Find it with `readlink /proc/*/exe | grep .mount_`. Killing
only the wrapper leaves `conduit` running holding a single-instance lock, which
makes the *next* launch hang identically and will invalidate your A/B tests.
